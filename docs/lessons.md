# 构建 paper-agent 的踩坑记录与知识总结

> 定位：这不是流水账，而是「现象 → 根因 → 修复 → 背后的通用知识」的问题集。
> 每一条都来自真实运行（不是理论风险），按主题分组，最后汇总成 Agent 构建的核心知识框架。
> 各里程碑的原始细节见 `docs/devlog/m0-m4.md`。

## 一、外部依赖不可靠：边界、降级与重试

### 1.1 数据源被网络屏蔽（M1）

- **现象**：arXiv / PubMed 从本机直连，TCP 连接在 ~0.2s 内被重置（curl HTTP 000）；Semantic Scholar 返回 429；OpenAlex / Europe PMC 正常。
- **根因**：网络层对特定站点的屏蔽；S2 匿名共享池拥挤。DNS 解析正常但 443/80 都不通，说明不是 DNS 问题。
- **修复**：数据源选型改为「按本机实测」——OpenAlex + Europe PMC 为主力（免 Key 直连），arXiv 适配器保留、支持 proxy、不可达时降级跳过。
- **通用知识**：
  - **选型要实测，不要信文档**。API 文档页面打不开 ≠ API 不可用；反之文档能打开 ≠ API 通。
  - 每个外部源都应有 `probe()` 健康检查（`pa doctor` 逐源探测），故障要能自诊断。
  - 降级设计：**单源失败不能拖垮整条流水线**，宁可少一个源也要出结果。

### 1.2 统一异常边界缺失，单点故障崩掉全局（M1）

- **现象**：`_http.py` 初版忘了把 `requests.RequestException` 包装成 `SourceUnavailable`，arXiv 的连接重置（10054）直接冒泡，崩掉了整个 `pa doctor`。
- **根因**：横切约定（统一异常包装）写在底层 helper 里，调用方以为「这个函数只会抛我认识的异常」。
- **修复**：`http_get` 统一包装；doctor 的 `_check_sources` 只捕 `SourceUnavailable`。
- **通用知识**：
  - **在系统边界定义自己的异常类型**（如 `SourceUnavailable`），外部库的原生异常不允许穿越分层边界——否则任何一个第三方库的异常类型变化都会击穿上层。
  - 这类「横切约定」必须有测试覆盖失败路径，否则最容易在重构中悄悄丢失。

### 1.3 网络时好时坏：重试不是可选项（M1/M4）

- **现象**：同一台机器，OpenAlex 这一刻 1.8s 返回，下一刻读超时（8s 不够）；`pa run` 检索阶段 OpenAlex 还偶发 429。
- **修复**：`http_get` 自动重试 1 次（间隔 2s）；后续 LLM 客户端同样内置退避重试（见 §2.1）。
- **通用知识**：
  - **只有幂等操作才能安全重试**。HTTP GET 天然幂等；POST 下单类操作重试会重复扣款。设计 API 交互时先想幂等性。
  - 指数退避（如 10s/20s/40s）优于固定间隔：给对方限流窗口留恢复时间。
  - 重试次数要有上限，超限后给出**明确的、人能读懂的错误**（"连续 4 次被限流"），而不是裸抛底层异常。

### 1.4 下载内容不可信：魔数校验（M1）

- **现象**：OpenAlex 的 `oa_url` 有时指向 HTML 落地页而非 PDF；ACM 直接 403 反爬；Wiley 返回 text/html。
- **修复**：下载器校验前 64KB 含 `%PDF` 魔数（或 Content-Type 声明 pdf），否则换下一个候选地址；失败原因逐条记录进 library.db 的 error 字段。
- **通用知识**：**凡是从外部拿到的文件都要验证内容类型**（魔数 > 扩展名 > Content-Type，可信度依次递减）；错误信息要保留现场（哪个 URL、什么响应），否则失败重试无从下手。

## 二、LLM 是不确定组件：解析、重问与限流

这是本项目问题最密集的一类，因为 LLM 的输出**本质上不可完全预测**。

### 2.1 免费档限流：批量调用必须内置退避（M4 体验测试）

- **现象**：`pa run` 对 8 篇论文连续做 LLM 分析，智谱免费档连续触发 429（错误码 1305），5 篇分析失败——成功 3、失败 5。
- **根因**：LLM 客户端是「一次调用一次请求」，没有重试；批处理场景下调用频率必然撞限流墙。
- **修复**：`chat()` 内置最多 4 次尝试、指数退避（10/20/40s），超限抛出明确错误。
- **通用知识**：
  - **写 Agent 前先问：这个 API 的限流策略是什么？**（RPM/TPM/并发数）免费档尤其苛刻。
  - 批处理速率要主动控制（每篇之间 sleep），而不是指望对方宽容。
  - 测试限流路径的方法：monkeypatch 假客户端抛 `RateLimitError`，断言重试次数（见 `tests/test_llm.py`）。

### 2.2 LLM 输出 JSON 不可信：三层防护（M2 → M4 持续加固）

- **现象**（逐步暴露）：① 回复被 ```` ```json ```` 围栏包裹；② JSON 前后有寒暄文字；③ 偶发空回复；④ JSON 中途截断（`Expecting ',' delimiter`）。
- **修复**（三层纵深）：
  1. `parse_json_reply`：剥围栏 → 直接解析 → 失败则截取首个 `{` 到最后一个 `}` 再解析；
  2. `normalize_experiment`：schema 校验 + 缺失字段补空值 + 类型修正，**永远不信任字段齐全**；
  3. `extract_experiment`：解析失败时**带上下文重问一次**（把坏回复和「只输出纯 JSON」的指令一起回传），累计 token 记账。
- **通用知识**：
  - **结构化输出 = prompt 约束 + 解析兜底 + 校验修复，三层缺一不可**。业界方案（JSON mode / function calling / 结构化输出 API）本质都是在补这三层。
  - 重问（self-repair）是成本最低的恢复手段：把失败输出回传，让模型自己改错，成功率远高于盲目重试。
  - 防编造的配套机制：逐字段 `confidence` + `unverified_claims`（「文中未说明」允许留空，比编造一个值好一万倍）。

### 2.3 展示层消毒：自由文本产物要过一道清洗（M2）

- **现象**：report.md 被 LLM 整体包进 ```` ```markdown ```` 围栏，打开文件第一行是代码围栏标记。
- **修复**：`strip_code_fence` 在生成时剥离；已生成的存量文件用脚本清洗。
- **通用知识**：**凡是 LLM 产出的、要给人看或要进下游的内容，都要有「消毒」步骤**——就像 Web 开发里对用户输入做转义。产物格式是契约，从写入源头保证，不要指望下游容忍。

### 2.4 LLM 生成代码的「自我纠缠」（M2）

- **现象**：`normalize_experiment` 的默认值处理初版被写成难以阅读的绕圈嵌套表达式（多重下标 + 永假分支），还引用了未定义顺序的字典。
- **修复**：重写为 5 行 dict comprehension。
- **通用知识**：**让 LLM 生成代码时，优先要求「平铺直叙」的实现**——复杂嵌套表达式是 LLM 最容易出错的形态；同时这也提醒我们，对生成的每一行都要 review，智能体生成的代码不因为「能跑」而免检。

### 2.5 「schema 说了算」不可靠：宽松 schema 的数据会流向展示层（M8）

- **现象**：Web 详情页实验结构渲染出一排 `[object Object]`。experiment.json 的 `method` 是嵌套对象、`datasets`/`experiment_steps` 是对象数组（LLM 输出了比字符串更丰富的结构），而前端只处理了字符串。
- **根因**：`normalize_experiment` 是**宽松校验**（缺失补空、类型尽量兼容，故意不拒绝丰富结构），下游却按「纯字符串 schema」写渲染——数据契约在两层之间理解不一致。
- **修复**：展示层改为递归渲染（对象展开为键值片段、数组转列表、空值统一 —）。
- **通用知识**：
  - **宽松入口 + 严格出口是一对**：校验层宽容是为了不丢数据，那么每个消费端都必须能处理「合法但形状任意」的数据；否则要么收紧校验、要么补渲染。
  - 端到端测试验不出这类问题（API 返回的 JSON 完全合法），**视觉验收才能抓到**——界面类交付必须过一眼真实渲染。

## 三、状态机是 Agent 的骨架：可重入与部分成功

### 3.1 状态语义不完整：分析失败的论文「卡在」indexed（M4 体验测试 → M6 根治）

- **现象**：`pa run` 里 5 篇论文 analyze 失败，但流水线继续把全文索引进向量库，状态标成 `indexed`。之后想重跑失败的论文，`pa analyze --all` 按 `parsed` 状态扫描——**扫不到它们**，失败论文从此成为管理盲区。
- **根因**：状态机只建模了「成功路径」（discovered → downloaded → parsed → analyzed → indexed），没有为「带着缺陷前进」的中间态建模。index 节点不检查 analyze 是否成功。
- **修复**（M6 落地，语义收敛）：**indexed 严格表示「分析 + 索引都完成」**——parsed（含分析失败）论文全文照样入索引（RAG 可检索），但状态保持 parsed、error 保留，重试扫描永远能发现它们；反向时序（先索引后单独分析）由 skip 分支补推进。
- **通用知识**：
  - **状态机是所有 Agent 的骨架**。断点续跑、增量处理、失败重试，全部建立在「每个实体的当前状态可查询、语义完整」之上。
  - 设计状态时必须回答：**部分成功算什么状态？失败态能不能被重试命令发现？** 只建模 happy path 的状态机，第一次遇到故障就会产生「管理盲区」。
  - 每个状态转换都要问一句「这个状态错了，谁还扫得到它」——把「索引成功」和「分析成功」两个概念耦合进同一个状态标签，就是盲区的根源。
  - 重试入口要支持**按 id 直达**，不能只靠状态扫描（本次 `pa analyze <id>` 能用，正是靠这个）。

### 3.2 幂等导入：重复执行不产生重复数据（M1/M2）

- **做法**：`pa add` 按文件内容哈希判重；`upsert_paper` 补空字段但绝不覆盖已有状态；`pa parse`/`index` 对已完成论文自动跳过。
- **通用知识**：**Agent 的每个操作都应设计成幂等的**——用户会重跑、定时任务会重跑、崩溃后会重跑。幂等 = 「执行一次和执行多次结果相同」，这是无人值守的前提。

## 四、代码组织：命名遮蔽与上帝文件

### 4.1 命名遮蔽：`pa chat` 命令干掉了 `llm.chat`（M4 体验测试）

- **现象**：`pa analyze` 全部报 `chat() got an unexpected keyword argument 'max_tokens'`；但同样的代码在 `pa run`（流水线）里正常。
- **根因**：cli.py 里 `from paper_agent.llm import chat` 导入了 LLM 函数，之后又定义了 Typer 命令 `def chat() -> None`——**同文件后定义的同名函数遮蔽了导入**。于是 `chat_fn=chat` 传进去的是那个无参数的命令对象。pipeline.py 自己导入 llm.chat，不受影响——「一处正常一处报错」正是遮蔽的典型指纹。
- **修复**：命令函数改名 `chat_cmd` + `@app.command("chat")` 显式指定命令名，两者解耦。
- **通用知识**：
  - **同一个模块里不要出现两个同名的东西**——函数遮蔽不报错、不警告，只在你最意想不到的调用路径上爆炸。
  - **入口文件（CLI）天然趋向「上帝模块」**：所有命令、所有导入都堆在一个文件里，冲突概率随行数增长。600+ 行的 cli.py 已经在付出代价（这次教训），拆分（命令分组到子模块）应在一期收尾时考虑。
  - 调试心法：「同一份代码 A 路径正常 B 路径报错」→ 先查两条路径引用的是不是**同名但不同物**的东西。

## 五、环境与工程细节（Windows 向）

| 问题 | 现象 | 对策 |
|---|---|---|
| 冷启动误判 | BGE-M3 首次调用 11.9s，复跑 2s | 偶发慢调用先想到冷启动；超时设置留余量 |
| shell 工具差异 | `ls`/`grep`/`tail`/`sleep` 不存在 | Windows 用 `dir`/`findstr`/PowerShell，或干脆用 Python 一把梭 |
| 控制台编码 | 管道下 rich 中文输出变 cp936，`findstr` 匹配中文失败 | 验证脚本用 Python 读管道，别依赖 shell 文本工具 |
| 多行脚本 | cmd 下 `python -c "多行代码"` 引号地狱、输出丢失 | 复杂验证写成临时 .py 文件执行后删除 |
| DOCX 标题 | `add_heading(level=0)` 产出 Title 样式而非 Heading 0 | `style.name == "title"` 单独处理 |
| URL 尾标点 | 正则把句尾 `.` 抓进链接 | 抓取后统一 rstrip 标点 |
| 空结果守卫 | 200 字符阈值（防扫描版 PDF）误杀合法短 DOCX | 守卫阈值按格式失败模式区分，不搞一刀切 |

## 六、知识框架总结：构建 Agent 的五条主线

把上面所有问题收拢，构建一个可靠的 Agent 系统需要掌握五件事：

1. **外部世界不可靠** → 系统边界统一异常、逐源健康检查、幂等重试 + 指数退避、优雅降级。
   *（§1 全部、§2.1）*

2. **LLM 不确定** → 解析三层防护（剥围栏/截取/校验补全）、失败重问、产物消毒、防编造标注。
   *（§2 全部）*

3. **状态机是骨架** → 每个实体生命周期可查询、语义完整（含部分成功）、操作幂等、失败可按 id 重入。
   *（§3 全部）*

4. **代码组织决定上限** → 异常不穿越边界、命名不遮蔽、入口文件克制、横切约定必须有测试。
   *（§1.2、§4、§2.4）*

5. **测试策略对准故障路径** → 离线注入（fake chat_fn / fake client / 临时文件构造），专测网络失败、限流、坏 JSON、空回复——happy path 的测试只验证了代码，故障路径的测试才验证了系统。
   *（各节修复中均含对应测试）*

> 一句话：**Agent 工程 = 把「不确定的外部世界 + 不确定的 LLM」装进「确定的状态机 + 确定的代码边界」里。**
