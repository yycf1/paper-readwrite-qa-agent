# M7 开发笔记 · FastAPI 服务层

M6 把业务编排下沉到 services/ 之后，Web 服务层只剩「参数解析 → 调服务 → JSON 序列化」，
这次拆分在 M7 直接兑现：路由层没有复制任何业务规则。

## 结构

- `server/routes.py`：REST 路由（/api/status、/papers、/papers/{id}、/search、
  /ask、/chat、/explore、/jobs/*）；
- `server/jobs.py`：长任务管理——流水线/单篇处理放后台线程，前端轮询
  `GET /api/jobs/{id}`；任务状态存进程内存（library.db 才是断点续跑的事实
  来源，服务重启后重跑同主题即恢复）；
- `server/app.py`：应用工厂 + `web/dist` 存在时同端口托管前端（M8 接入）；
- `pa serve` 命令（admin.py）：uvicorn 启动，`--reload` 开发模式。

## 关键决策

**长任务 vs 同步请求**：检索/问答/对话在 HTTP 请求内同步完成（几秒到几十秒，
前端 loading 即可）；`pa run` 全流水线（可能十几分钟）必须走 202 + 轮询，
否则请求超时、用户无进度反馈。单篇「一键处理」（约 1-3 分钟）也归入任务。

**每请求独立 Library 连接**：SQLite 文件库，线程内各自 `paths.library(cfg)`，
不存在共享连接的并发问题——这是 M1「账本为唯一事实来源」设计的红利。

**错误码语义**：参数/未找到 → 400/404；环境问题（缺 Key）→ 503；
请求体校验交给 Pydantic（自动 422）。LLM 失败在 service 层已降级为结果内
notes，不会变成 500。

## 实测

- TestClient 离线测试 8 项（任务生命周期含轮询）；
- 真实库上手工过全部端点：status/papers 列表筛选/详情（含 experiment +
  23 万字符全文）/chat 真实 LLM 意图路由（「库里现在有多少篇论文」→ status
  意图 → 正确计数）/ask 全库（范围外问题诚实回答「未提及」）与限定单篇
  （带 [编号] 出处回答结论）。

顺带发现一处数据问题：早期（thinking 修复前）生成的 report.md 有 2 字节空
文件——API 忠实返回了空字符串。这正是 M5 教训的遗留物，新分析已由兜底防护。
