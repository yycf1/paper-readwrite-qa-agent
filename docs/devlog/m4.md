# M4 开发笔记 · 编排整合与打磨

## 交付物

- `paths.py`：目录/账本助手独立模块，CLI 与流水线共用（消除漂移）；
- `graph/pipeline.py`：六节点线性图 search→select→download→parse→analyze→index；
  阶段逻辑是普通函数（可脱离图测试），图节点只做薄封装；
- `graph/route.py`：意图分类 search/qa/status/exit/help，LLM 失败退化启发式；
- CLI：`pa run`（阶段统计 + 警告汇总）、`pa chat`（自然语言 REPL）；
- 单测 59 个全绿：fake 源/下载/解析/LLM/向量库走真实图。

## 实测结果（真实网络 + 真实库）

| 项 | 结果 |
|---|---|
| `pa run`（GNN 推荐主题） | 检索 20，新入库 11，选 top-2；arXiv 降级不阻塞 |
| `pa run`（ViT 分割主题） | 选 top-3 全为仅摘要 → 结余回填下载 3 篇（1 成功 2 出版商 403）→ 解析 1 篇 → 34 块入库 |
| analyze 无 Key 降级 | 「知识提取跳过：未配置 LLM API Key」，整阶段跳过，索引照常完成 |
| 断点续跑 | 同主题重跑：已 indexed 不再处理、已 attempted 不重复入库，各阶段计数归零 |
| `pa chat` 无 Key | 启发式路由正常（status/exit 验证）；LLM 路由待 Key |

## 关键决策与踩坑

1. **library.db 就是 checkpoint**：不引入 LangGraph SqliteSaver——每个阶段以论文状态决定跳过/执行并独立提交，任何一步中断后重跑即续。状态机的五态语义在此处兑现了全部价值。
2. **引用数优先选文 vs OA 现实的矛盾**：高引论文多为闭源（Elsevier/ACM/IEEE），无人值守 top-N 经常全是「仅摘要」，预算全浪费。加「结余回填」：selected 处理完后，预算按引用数继续给其余有 OA 链接的 discovered 论文。这保持了 PLAN 的选文语义，同时让无人值守真的能攒出可问答的全文库。
3. **analyze 失败要「整阶段降级」而不是逐篇撞墙**：缺 Key/平台不可达是环境问题，先发一次探针调用确认，失败则整个阶段跳过；单篇 LLM 偶发失败才逐篇记 error 继续。错误分类决定重试粒度。
4. **静默失败的脚本替换**：用脚本把 CLI 目录助手切到 paths 模块时，断言失败被 cmd 吞掉（无输出、我没查 exit code），后续命令照常跑造成「已重构」假象，直到 chat 引用 paths 才炸。教训：**重构必须立刻跑受影响路径的测试，且不信任被吞掉的输出**。
5. **管道输入的编码坑**：Windows cmd 管道喂中文是 GBK 字节，rich 按 UTF-8 读直接 UnicodeDecodeError 崩掉 REPL。交互式键盘输入不受影响（ReadConsoleW），但 REPL 对解码错误做了容错。
6. **token 用量**：analyze 在产物与运行统计中记账；chat 意图分类是 ~100 token 级小调用，不单独记账（待 LLM 实测后再定是否值得）。
