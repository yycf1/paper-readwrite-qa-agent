# M6 开发笔记 · 健壮性收尾与 Web 化地基

M6 的定位：把 M0–M5 积累的三笔「已知债」还掉（状态机盲区、无 CI、上帝文件），
同时为 Web 界面打好地基——service 层下沉后，CLI 与 FastAPI 共用同一套业务编排。

## 1. 状态机盲区根治（最重要的修复）

**问题**：`run_index` 和 `pa index` 把 parsed 状态（含「分析失败带 error」）的论文
也索引进去，然后**一律标成 indexed 并清掉 error**。后果有两个：

1. `pa analyze` 按 parsed 状态扫描重试，永远扫不到这批论文——它们在账本里
   看起来「已完成」，实际上知识提取从未成功；
2. 失败痕迹（error 字段）被抹掉，故障不可观测。

这个 bug 在 M4 体验测试时被发现过，当时用 `pa analyze <id>` 按直达重试绕过；
M6 从根上修：**indexed 严格表示「分析 + 索引都完成」**。

修复后的语义矩阵：

| 论文状态 | 索引行为 | 状态推进 |
|---|---|---|
| analyzed（含先索引后分析时序） | 全文入库 | → indexed |
| parsed（分析失败/未跑） | 全文照样入库（RAG 可检索） | **保持 parsed**，error 保留，`pa analyze` 可重试 |
| discovered（仅摘要） | 摘要单块入库 | 不改状态（下载成功后可升级全文索引） |

「先索引后分析」的时序也要处理：用户可能先 `pa index` 再单独 `pa analyze`，
此时向量库已有全文但状态停在 analyzed——run_index 的 skip 分支会补推进到 indexed。

**教训**：状态机里每个状态转换都要问一句「这个状态错了，谁还扫得到它」。
把「索引成功」和「分析成功」两个概念耦合进同一个状态标签，就是盲区的根源。

`.github/workflows/ci.yml`：Python 3.11 / 3.13 双版本矩阵，uv 安装依赖 +

## 3. service 层下沉 + CLI 拆包

M5 结束时 cli.py 已 1029 行，是典型的「上帝文件」：命令注册、业务编排、
终端渲染、环境自检全部混在一起。Web 化后每条业务都要有第二个入口，
继续长在 CLI 里就得复制一遍流程。M6 的拆法：

- **services/search.py**：检索编排（查询优化 → 多源 → 校验 → 去重 → 入库），
  返回 SearchOutcome（新入库/候选数/过程 notes/每源命中）；CLI 是「渲染壳」，
  未来 FastAPI 是「JSON 壳」，共用同一套降级与去重规则。
- **services/assistant.py**：对话单轮处理（意图路由 → 分发执行），
  handle_message 永不抛异常（错误转回复文本），返回结构化 AssistantReply。
- **cli/ 包**：core.py（app + console + 渲染辅助）、ingest.py（生命周期六命令）、
  qa.py（ask/eval）、flow.py（run/chat/status）、admin.py（version/doctor）。

顺手切掉一处反向依赖：tools.py 曾延迟导入 cli.py 的 SOURCE_MODULES（工具层
依赖表现层，方向反了），现在收编进 tools.py，services 与 cli 都从它导入。

**教训**：拆包的时机不是「代码长了就拆」，而是「第二个入口出现之前」。
service 层是 CLI/Web/二期 MCP server 三方共用的接缝，提前于 FastAPI 落地，
路由层就只剩参数解析和响应格式化。

## 4. qa.py 空回复兜底

GLM 混合推理模型的已知隐患（M5 发现）：思考 tokens 吃光 max_tokens 时
content 为空。M5 已给分类/打分/explore 禁用 thinking，但问答链用的是默认
thinking——补上「空回复 → 禁用思考重问一次」的兜底，正常路径零额外开销。

## 5. 顺带的健壮性加固

  （服务层测试用简化 route 触发了 KeyError——防御性不足在测试里现形）；
- `pa chat` 的业务逻辑全部收进 handle_message 后，REPL 循环只剩 20 行。
